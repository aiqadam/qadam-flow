# @aiqadam/platform

## 2.0.0

### Major Changes

- e743ad0: A step or an agent tool pinned to a qadam version this instance does not have no longer silently runs a different build (ADR-0003, #779). The engine runs the pin from the qadam version store or from the image's build of that same version; for a release pin that neither holds, it runs the image's build only inside the pin's caret range (never another major, on `0.x` never another minor, never an older build) and logs `The pinned version is not available, running the image's build inside the pin's caret range instead`; otherwise the run fails with the pin named. A snapshot pin (`x.y.z-main.<n>`) is exact: no other build stands in for it and it is never installed from a registry. The worker also checks the qadams that an agent step uses as tools before the run, as it does for steps, so a custom qadam used only as an agent tool is installed and an unavailable one (or a tool whose version is no version) fails the flow with its pin named; `ap_validate_flow` and `ap_flow_structure` now report tool pins. Flows that only ran through the old fallback or a stale worker-cache answer now fail and need a re-pin: see "Unreleased" in docs/install/configuration/breaking-changes.mdx. The worker's cache moves to `cache/v13`: its first jobs after the upgrade look every pin up again and reinstall custom qadams, and the old `cache/v12` is removed once idle.
- 9af2e0c: 2.0.0, the first release since 1.1.0 and the first under ADR-0001: the root package.json now holds the last released version (1.1.0 until this release), and images built from `main` report `<next>-main.<n>` (#798). The operator-facing changes are under "2.0.0" and "Unreleased" in docs/install/configuration/breaking-changes.mdx.

### Minor Changes

- 8ba81df: Workers in the `UNSANDBOXED` and `SANDBOX_CODE_ONLY` execution modes run an official qadam step from the qadam version store when the store holds the pinned version, with `@aiqadam/*` and `zod` provided by the platform (ADR-0003, #779). Workers now read `AP_QADAM_VERSION_STORE_PATH`. No image puts versions in the store yet (#807), so installs run the bundled qadams as before.
  
  Workers must mount the qadam version store read-only: a worker whose store is not on a read-only mount (read from its mount table; permission bits do not count) does not use it outside `AP_ENVIRONMENT=dev`, runs the bundled qadams, and logs "mount the qadam version store read-only on workers". The bundled `docker-compose.yml` mounts `qadam_versions` with `:ro` on workers; an install with an older or custom compose file, or another orchestrator, needs the same change to use the store.
- f092790: Steps pinned to a qadam built for a framework version this release no longer runs are now marked in the flow builder (ADR-0002, #803): a warning icon on the step in the canvas, and a "Framework version no longer supported" notice with the remedy ("update this step") in the step settings. The mark is informational and never blocks editing; no flow is disabled. It is read through a new project-scoped route, `GET /v1/framework-census/flow-version?flowId=…&flowVersionId=…`, reachable by any member of the flow's project with read access; it answers nothing while this release has retired no framework version.
- 58d09ab: A step pinned to a qadam version this instance cannot have (one that was never published, the stale pins an image upgrade strands) is now moved to the image's build of the same qadam in the draft being published when its flow is published, instead of only running on it (ADR-0003, #808, first slice). The move happens only when the image's version is inside the pin's caret range, the props are compatible where metadata for the pinned version exists, and the target loaded; each move is written to an audit record (new `qadam_pin_move` table) together with the rewrite of the step's pin, and a platform admin can list the records and revert a move through `/v1/qadam-pin-moves`, which restores the old pin in a draft (the published version keeps running until it is published). A step that is not moved keeps its pin, and no flow is disabled. The run-time stand-in that runs a stale release pin on the image's build inside its caret range is unchanged for flows that have not been published since, and enabling a flow does not move pins.
- c639f50: A flow export rewrites a pre-release (`x.y.z-main.<n>`) qadam pin to the newest compatible release, or to `^<base>` with the step listed as exported-unresolved when none passes the props check; the importer marks such a step "update this step" (ADR-0004, #853). `GET /v1/flows/:id/template` takes `sameInstance` (templates that stay on the instance keep their pins) and `keepSnapshots` (an explicit opt-in that keeps the pins and embeds each snapshot's `metadata.json`), in the UI export menu and in `ap_export_flow`. Instances running release images have no pre-release pins, so an export there is unchanged. What a qadam reaches through the framework changes only additively: `PopulatedFlow`, which the framework re-exports, gains optional `exportedUnresolvedPin` on a step's settings; none of the new exports is re-exported.
- 94ebec9: At start-up, `AP_QADAM_SNAPSHOT_POLICY=follow` moves each draft's available qadam pin to the newest build the image ships when that build is newer and inside the pin's caret range, with the same props and load checks, audit record and revert as the unavailable-version move (#808), under the new move cause `SNAPSHOT_FOLLOW` (ADR-0004, #854). A pin already at the image's build is a no-op, so the pass runs once per boot. What it moves depends on the instance (ADR-0004): a `-main.<n>` instance, where `follow` is the default, moves release pins and snapshot pins, while a release instance moves snapshot pins only and never moves a release pin. A release pin's props are checked against the catalogue, whose address answers 404 until #778, so on a real instance a release pin stays for now; a snapshot pin is checked against the version store. `pin` (the default on a release instance) never rewrites an available pin. Surfacing this in the builder and MCP (the "pre-release build" label, "update available" and the hold) and the store GC / revert-target retention are follow-ups (#855, #478).
- f00a855: The `follow` hold state from #854 is now visible in the builder (ADR-0004, #855). When a person reverts a pin move, `follow` holds the step and does not move it again until its version changes; the step settings of a step held for the open flow now show a "held step" label that says so. The label is a fact, not a fault — it is informational and never blocks editing. The hold is read through a new project-scoped route, `GET /v1/qadam-pin-moves/held?flowId=…`, reachable by any member of the flow's project with read access (the platform-admin list/get/revert routes are unchanged).
- 4ac14f0: A step pinned to a pre-release qadam build (`x.y.z-main.<n>`, the version a build from `main` gives a changed qadam) is now labelled "pre-release build" in the builder step settings, marked on its line and carried as a positive `preReleaseBuild` flag by `ap_flow_structure`, and reported by `ap_validate_flow` as an informational note that never blocks publishing. It is a fact, not a fault: the pin resolves and the step runs exactly the build it names, so it is never surfaced as a warning or an unavailable version. "Update available" pointing at the release and the `follow` hold state remain later slices (ADR-0004, #855).
- 3f8d799: A step pinned to a pre-release qadam build (`x.y.z-main.<n>`, the version a build from `main` gives a changed qadam) now shows "Update available" in the builder step settings once the instance knows a released version of the same qadam inside the pin's caret range — the graduation ADR-0004 describes, where `^1.3.0-main.412` contains the base release `1.3.0` and later patches like `1.3.2`. The offer names the newest such release and opens the existing update dialog on exactly that version; it never rewrites the pin on its own. The `follow` hold state from #854 remains a later slice (ADR-0004, #855).

### Patch Changes

- dbb05fe: The signature check on `@aiqadam/*` packages (ADR-0003, #780) no longer repeats its registry reads after every worker restart. It keeps each verified npm signature in a ledger next to the workspace's `bun.lock` and checks it again offline against npm's pinned keys, so a restarted worker needs the registry only for a package it never verified, one whose bytes changed, or a ledger that was lost or edited; those are still refused when the registry is unreachable. The same ledger format (`qadam-signatures.json`) is available beside the qadam version store for the fetch of #806. Only matters with `AP_OFFICIAL_QADAMS_INSTALL_ENABLED` on, which stays off; nothing changes in a default install.
