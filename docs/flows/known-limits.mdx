<Note>
The **Cloud** column shows the limits inherited from the upstream Activepieces
Cloud configuration — historical reference only. On **self-hosted** Qadam Flow
installations every limit is configurable through the environment variable
shown in the table; the **Self-hosted default** column lists the value applied
when the variable is unset.
</Note>

### Execution

| Limit | Cloud | Env var | Self-hosted default |
|---|---|---|---|
| Flow run timeout | 10 min | `AP_FLOW_TIMEOUT_SECONDS` | `600` |
| Worker process memory | 1 GB | `AP_SANDBOX_MEMORY_LIMIT` (KB) | `1048576` |
| Paused flow lifetime | 30 days | `AP_PAUSED_FLOW_TIMEOUT_DAYS` | `30` |
| Worker concurrency (per worker) | 10 | `AP_WORKER_CONCURRENCY` | `5` |

<Tip>
Flows paused by **Wait for Approval** or **Delay** do **not** count toward the
flow run timeout — the timeout only counts active execution time.
</Tip>

<Tip>
The memory limit is measured for the entire Node.js process running the flow.
About 300 MB of that is overhead for a warm process with qadams loaded.
</Tip>

<Tip>
To handle longer processes, split them into multiple flows — e.g. one flow calls
another via webhook, or each flow processes a smaller batch of items.
</Tip>

### Files & flow run logs

<Info>
Files emitted by actions or triggers are persisted to the database or S3 so the
flow can retry from a later step. The log size limit applies to the combined
inputs and outputs of every step in a single run; step outputs above the slice
threshold are offloaded to object storage and re-hydrated on demand instead of
sitting in worker memory.
</Info>

| Limit | Cloud | Env var | Self-hosted default |
|---|---|---|---|
| Step file size | 10 MB | `AP_MAX_FILE_SIZE_MB` | `25` |
| Flow run log size (combined inputs + outputs, includes sliced payloads) | 25 MB | `AP_MAX_FLOW_RUN_LOG_SIZE_MB` | `50` |
| Step output slice threshold | 32 KB | `AP_FLOW_RUN_LOG_SLICE_THRESHOLD_KB` | `32` |
| Step input truncate threshold | 2 KB | `AP_FLOW_RUN_LOG_INPUT_TRUNCATE_THRESHOLD_KB` | `2` |

#### How it works

- **Input** — values above `AP_FLOW_RUN_LOG_INPUT_TRUNCATE_THRESHOLD_KB` are
  replaced with a placeholder in the log; the step still receives the full
  value at runtime.
- **Output** — outputs above `AP_FLOW_RUN_LOG_SLICE_THRESHOLD_KB` are offloaded
  to object storage and replaced with a reference in the log; the payload is
  re-hydrated on demand.
- **Total** — the cumulative size of inputs and outputs (counting the
  **original** size of offloaded outputs) is capped by
  `AP_MAX_FLOW_RUN_LOG_SIZE_MB`. Runs that exceed it end with status
  `LOG_SIZE_EXCEEDED`.

<Warning>
A run that produces enough cumulative output to exceed
`AP_MAX_FLOW_RUN_LOG_SIZE_MB` ends with status `LOG_SIZE_EXCEEDED`, regardless
of how many individual outputs were offloaded to object storage. Lowering
`AP_FLOW_RUN_LOG_SLICE_THRESHOLD_KB` will not buy more log headroom — only
raising `AP_MAX_FLOW_RUN_LOG_SIZE_MB` does.
</Warning>

### Webhooks

| Limit | Cloud | Env var | Self-hosted default |
|---|---|---|---|
| Sync webhook response timeout | 30 s | `AP_WEBHOOK_TIMEOUT_SECONDS` | `30` |
| Max webhook payload size | 5 MB | `AP_MAX_WEBHOOK_PAYLOAD_SIZE_MB` | `25` |
| Webhook payload inline threshold | 1024 KB | `AP_WEBHOOK_PAYLOAD_INLINE_THRESHOLD_KB` | `512` |
| Sync webhook backpressure | — | `AP_SYNC_WEBHOOK_BACKPRESSURE_ENABLED` | `true` |
| Sync webhook backpressure `Retry-After` | — | `AP_SYNC_WEBHOOK_BACKPRESSURE_RETRY_AFTER_SECONDS` | `5` |

<Tip>
For synchronous webhook requests (URLs ending in `/sync`), Qadam Flow waits
up to the response timeout for the flow to answer. A flow that finishes without
a Return Response step answers 204 right away, and a failed flow answers 500. If
the timeout ends before the flow answers, you get HTTP 504 — a run already in
progress keeps going in the background, but a run that had not started dispatch
yet fails outright instead of running late for a caller that has stopped
waiting (see Dispatch below). Either way, retrying the request starts the flow
again from the beginning. Payloads above the inline threshold are offloaded
from Redis to file storage to protect Redis memory; smaller payloads stay
inline for the fastest path.
</Tip>

#### Dispatch: acceptance to first step

Accepting a sync webhook call and starting the run are two different moments —
the run sits `QUEUED` until a worker picks it up. Three things bound and surface
that gap:

- **A dispatch deadline.** The run's deadline is the same instant its caller's
  own timeout budget expires — the default `AP_WEBHOOK_TIMEOUT_SECONDS`, or a
  longer per-call override such as MCP's. This applies uniformly to every sync
  webhook path, including the draft/testing sync route and MCP's
  response-returning tool calls — there is no exemption for test or draft
  runs. If a worker dequeues the job's first delivery after that instant has
  passed, it fails the run explicitly (status `FAILED`, with an internal error
  recording that the dispatch deadline was exceeded) instead of executing it
  late, after the caller has already been answered a 504. A run that has
  already started keeps going exactly as before — only a run whose first
  dispatch attempt never started is affected. This is a wall-clock comparison
  between the server that accepted the request and the worker that later
  dequeues it, so it assumes the two have synchronized clocks (NTP).
- **Observability.** Every flow run exposes a derived `dispatchWaitMs` field
  (`GET /v1/flow-runs` and `GET /v1/flow-runs/:id`): the time between the run
  being accepted and the engine actually beginning execution. It is `null`
  until the run starts. Two cases are worth knowing when reading it:
  - An **inline** subflow call (`dispatchMode: INLINE`) always reads `0` — it
    executes synchronously in its parent's own engine process, so there is no
    queue wait to measure.
  - A run **retried** with "Retry from failed step" reuses the same row.
    `dispatchWaitMs` on a retried run reflects time since the run's *original*
    creation, not the latest retry's own queue wait — read it as a lifetime
    figure, not a live per-attempt health metric.
- **Backpressure at submit time.** A sync webhook call can be refused upfront,
  before a run is even created, with `503` and a `Retry-After` header
  (`AP_SYNC_WEBHOOK_BACKPRESSURE_RETRY_AFTER_SECONDS`), when every worker slot
  is already busy **and** a full extra round of runs is already waiting behind
  them. The slot count is read live from the connected worker registry
  (`AP_WORKER_CONCURRENCY` × online workers), not a fixed number, so it tracks
  however many workers and replicas are actually online. This check runs
  against one shared job queue for the whole instance — it is **not** scoped
  per project or per platform, so a busy project or platform can cause
  another's sync webhooks to be refused too. Set
  `AP_SYNC_WEBHOOK_BACKPRESSURE_ENABLED=false` to disable this check.

<Info>
**Dispatch throughput ceiling.** With one sandbox per worker concurrency slot,
the instance's maximum sync-webhook throughput is bounded by:

```
max throughput ≈ (worker replicas × AP_WORKER_CONCURRENCY) ÷ run duration
latency at offered concurrency C ≈ C ÷ max throughput   (for C > slot count)
```

At the shipped defaults (`replicas: 5`, `AP_WORKER_CONCURRENCY=5` → 25 slots)
and a ~6 s flow, that is ~4 runs/s, and 40 concurrent callers see roughly 10 s
each — ordinary queueing against a saturated instance, not a stall. The 25
slots are shared with every other job type (polling triggers, property/
validation calls), so a busy instance gets less than the formula's best case.
Raise throughput with more worker replicas or `AP_WORKER_CONCURRENCY`
(memory-bound, one sandbox per slot), or shorten the flow itself.
</Info>

### Key / value storage

Used by the built-in **Store** qadam and any qadam that calls `context.store`.

| Limit | Value |
|---|---|
| Maximum key length | 128 characters |
| Maximum value size | 512 KB |

These limits are not configurable.
