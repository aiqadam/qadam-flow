The qadam version store is a directory on a persistent volume where the server keeps the code of each qadam version it holds, by name and exact version. It is how [ADR-0003](https://github.com/aiqadam/qadam-flow/blob/main/adr/0003-official-qadams-run-from-a-versioned-local-store.md) makes a flow step pinned to `tables@0.5.1` run the code of `tables@0.5.1` across server upgrades, instead of whatever version the current image bundles.

<Warning>
The store is only partly in use. A worker runs an official qadam version from the store when the store holds it, in the `UNSANDBOXED` and `SANDBOX_CODE_ONLY` execution modes (see [How a step finds its code](#how-a-step-finds-its-code)). But no image ships versions to put in it before [#807](https://github.com/aiqadam/qadam-flow/issues/807), so on a real install the store is empty and flows run the qadams bundled with the image, as [Qadam syncing & versioning](/install/architecture/qadam-syncing) describes. The builder's qadam metadata, the sandboxed execution modes and custom qadams do not use the store yet ([#779](https://github.com/aiqadam/qadam-flow/issues/779)). The volume exists and the server prepares it on every start, so an install that adds it now needs no change later.
</Warning>

## Where it lives

The bundled `docker-compose.yml` mounts the named volume `qadam_versions` at `/var/lib/qadam-flow/qadam-versions` on the `app` service, and read-only on every `worker` replica: only the app writes the store, and workers run flow code that must not be able to change code every tenant runs. Re-running the [installer](/install/options/docker) on an existing install adds the volume; nothing else changes.

A worker checks this from its mount table (`/proc/self/mountinfo`): the mount that holds the store, and every mount inside it, must be read-only. Directory permissions do not count, so a worker running as any user on a `:ro` mount passes, and a `chmod 555` store on a writable volume does not. A worker whose store fails the check does not use it, runs the qadams bundled with the image, and logs `The qadam version store is not on a read-only mount … mount the qadam version store read-only on workers`; in a development environment it uses it anyway, with that warning. Do not combine [`docker-compose.sandboxed.yml`](/install/architecture/sandboxing) with the `UNSANDBOXED` or `SANDBOX_CODE_ONLY` execution mode: it grants workers `CAP_SYS_ADMIN`, which lets flow code in a forked engine remount the store read-write.

If you run the containers another way, mount one volume at that path on the app (read-write) and every worker (read-only), or set `AP_QADAM_VERSION_STORE_PATH` to where you mounted it. Three requirements:

- **Outside any directory with a `node_modules`.** A stored version finds packages the way Node does, upward from its own directory, and must find only what the platform provides. The store refuses to open at or below a directory that contains a `node_modules`, such as the app's own `/usr/src/app`.
- **A case-sensitive filesystem.** Platform ids and prerelease versions can differ only by case. A Docker named volume is case-sensitive; a bind mount of a macOS or Windows folder usually is not. On a case-insensitive filesystem the store refuses to open.
- **One volume per host type.** A qadam version that ships native modules runs only where it was built: the same OS and CPU, the same Node major version, and a C library at least as new. Do not share one volume between `amd64` and `arm64` containers. The store keeps a version it cannot run here instead of replacing it, so another host that can run it still finds it.

When the store cannot open, the app logs `[qadamVersionStore] The qadam version store is unavailable` with the reason — at info level in a development environment, where `/var/lib` is usually not writable — and runs as before. To use the store in a development tree, set `AP_QADAM_VERSION_STORE_PATH` to a writable directory outside the repository.

## What the server does at start-up

When the app starts, it creates the store's directories if they are missing, removes what an interrupted write left behind, and copies into the store every qadam version the image ships. With several app replicas, one seeds at a time and the others find the work done. Each start logs one line:

```text
[qadamVersionStore] Seeded the qadam version store from the image {"status":"no-seed","stored":0,"present":0,"kept":0,"failed":0,"durationMs":3}
```

`status` is `no-seed` on every image until [#807](https://github.com/aiqadam/qadam-flow/issues/807) adds the versions to ship. `kept` counts versions in the store that this release cannot use, for example ones a later release wrote before you rolled back; they are left in place for that release. A seed that fails is logged as a warning and does not stop the app.

## How a step finds its code

When a worker in the `UNSANDBOXED` or `SANDBOX_CODE_ONLY` execution mode starts, it opens the store at `AP_QADAM_VERSION_STORE_PATH` for reading only, and logs which way it went:

```text
[qadamVersionStore] Steps in forked engines load official qadam versions from the qadam version store when it holds them
[qadamVersionStore] The qadam version store is unavailable; steps load the qadams bundled with the image {"reason":"..."}
```

Then, for a step pinned to an official qadam at an exact version, such as `@aiqadam/qadam-tables@0.5.1`:

1. If the store holds `@aiqadam/qadam-tables` `0.5.1` and it checks out, the step runs that code, even when the image bundles the same version.
2. Otherwise the step runs the image's build of that same version.
3. Otherwise, for a release pin only, the step runs the image's build of the qadam at another release inside the pin's caret range (the same major, or on `0.x` the same minor, never below the pin), and the worker says so once per pin and engine process: `The pinned version is not available, running the image's build inside the pin's caret range instead`. That is the stand-in for the [unavailable-version fallback](https://github.com/aiqadam/qadam-flow/issues/808), which will make the move with a check and an audit record, and it goes when that lands.
4. Otherwise the run fails with the pin named, for example `Qadam not found for package: @aiqadam/qadam-tables@0.5.1. The qadam version store and the image hold no @aiqadam/qadam-tables@0.5.1, and the image's build 1.0.0 is outside ^0.5.1.` Nothing runs a different major, a `0.x` minor below or above the pin, an older build than the pin, or any other build for a snapshot pin (`x.y.z-main.<n>`, [ADR-0004](https://github.com/aiqadam/qadam-flow/blob/main/adr/0004-main-builds-give-changed-packages-their-own-prerelease-versions.md)): a snapshot is exact, is never published, and is moved only by that fallback.

Steps that an agent step uses as tools are provisioned like steps: the worker checks every PIECE tool's pin before the run, and the run fails with the pin named when a tool's qadam is unavailable. A tool list that a variable supplies at run time cannot be checked ahead of the run; the engine applies the same rules when it loads the tool.

A stored version that is damaged or that this release cannot use is skipped, with one warning per version and engine process in the worker's log:

```text
[qadamVersionStore] The stored version cannot be used, loading the image's build instead {"qadam":"@aiqadam/qadam-tables@0.5.1","status":"damaged","reason":"integrity.json is missing"}
```

The `[qadamLoader] cold load` line that the worker writes the first time it loads a qadam says where the code came from in `source`: `store`, `bundled`, `bundled-fallback` (step 3), `installed` or `dev`.

### Libraries the platform provides

A stored version carries its own code and its third-party dependencies. `@aiqadam/qadams-framework`, `@aiqadam/qadams-common`, `@aiqadam/shared` and `zod` come from the platform, so every qadam a worker runs shares one copy of each with the qadams bundled in the image. When code in a stored version loads a package:

1. one of those four packages is the platform's copy. Only a third-party dependency inside the version may use a private copy nested under it;
2. any other package must be inside the version itself;
3. nothing else is found. A stored version does not fall back to `NODE_PATH`, `$HOME/.node_modules` or other global folders, so it cannot silently run on a library the server happens to have. It fails with "Cannot find module" instead.

This keeps a version on the libraries it is meant to run with. It is not a security boundary: a qadam runs with the worker's rights, and isolating flow code is the job of the [execution mode](/install/architecture/sandboxing).

## Layout

```text
qadam-versions/
  qadams/
    @aiqadam/qadam-tables/0.5.1/          an official qadam version
    _platform/<platformId>/<name>/1.0.0/  a custom qadam of one platform
  qadam-signatures.json                   npm signatures verified for fetched versions (#806)
```

Each version directory holds the qadam's code (`package.json`, its entry point, and `node_modules` when the version needs it), `metadata.json`, and `integrity.json`. The store writes a version in a staging directory and renames it into place, so a version is either complete or absent. It never overwrites a version: a version is never republished (see [Qadam versioning](/build-qadams/qadam-reference/qadam-versioning)). `integrity.json` records a sha512 digest of every file. Only a damaged version — its record missing or not readable as JSON, or naming another version — is replaced the next time the server stores that version. A version written by a later release, built for another host, or that the server cannot read because of a filesystem error is never replaced.

`qadam-signatures.json` is where the server keeps the npm signature of each official version it verifies when it fetches one ([#806](https://github.com/aiqadam/qadam-flow/issues/806); nothing fetches yet, so the file does not exist today), so a restart does not need the registry to know that version was signed. It holds the signature itself rather than a yes: each time it is read the signature is checked again against npm's public keys that ship in the image, for exactly that version and the integrity of the tarball it came from. If the file is deleted, edited or unreadable, or a version has no record, the server asks the registry again, and without a registry that version is not accepted as verified. Versions seeded from the image are trusted as the image is, and no npm signature is asked of them. Losing the file costs registry reads, never a version.

Custom qadams get a directory per platform, so one platform's qadams are never found under another platform's name. Nothing writes custom qadams to the store yet; they are installed as described in [Manage qadams](/admin-guide/guides/manage-qadams) until resolution moves to the store.

## Back up and move

Keep the volume with your database when you back up or move an install. Today every version in it can be seeded again, so losing it costs nothing. Once the server fetches versions on demand ([#806](https://github.com/aiqadam/qadam-flow/issues/806)), a restored store saves fetching them again, and an install with no access to a registry depends on it.

`docker compose down -v` deletes the volume together with the database.
