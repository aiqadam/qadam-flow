Flow code — Code steps and qadam actions — always runs inside a **sandbox** that wraps the engine process. `AP_EXECUTION_MODE` decides which sandbox, and it is the most consequential security choice in a self-hosted deployment: it decides whether a malicious flow is contained to one worker pod or can reach the kernel.

## Execution Modes

<Snippet file="execution-mode.mdx" />

<Tip>
**For enterprise deployments, use `SANDBOX_CODE_ONLY` (V8 isolation).** It is the only mode that is both multi-tenant-safe *and* runs as an unprivileged container — which is what Qadam Flow Cloud uses, and what fits inside a standard Kubernetes security baseline.
</Tip>

## Why V8 Sandboxing Exists

`SANDBOX_PROCESS` uses the `isolate` binary, which creates fresh Linux namespaces per run. That needs `CAP_SYS_ADMIN` — in practice, `privileged: true` on the container. V8 Sandboxing exists so you don't have to grant that.

### A concrete K8s example

You run Qadam Flow in your own Kubernetes cluster, next to a Salesforce-sync service and a finance-analytics pod. A customer ships a malicious Code step.

- **With `SANDBOX_PROCESS`** — the worker pod is privileged. A kernel exploit escapes to the host, reads the service-account token, hits the Kubernetes API, and pivots to the Salesforce pod and the finance DB. Blast radius: **your whole cluster**.
- **With `SANDBOX_CODE_ONLY`** — the worker has no special capabilities. The Code step runs inside a fresh V8 isolate (no `require`, no filesystem, no npm). Blast radius: **that one worker pod**.

V8 isolation is how you get multi-tenant code safety without handing a workflow engine kernel-level access to everything sharing the cluster.

<Warning>
Only choose `SANDBOX_PROCESS` if you genuinely need arbitrary `npm` packages in Code steps, and run it on a dedicated node pool. A privileged Qadam Flow worker should never share a node with unrelated workloads.
</Warning>

## How Each Mode Works

### `fork()` + V8 — `UNSANDBOXED`, `SANDBOX_CODE_ONLY`

The engine runs as a plain `child_process.fork` with a memory cap. In `SANDBOX_CODE_ONLY`, every Code step is additionally wrapped in a fresh [`isolated-vm`](https://www.npmjs.com/package/isolated-vm) context — 128 MB per isolate, `require` removed, disposed after the step. No Linux-namespace machinery, no `CAP_SYS_ADMIN`, no privileged container. Sandboxes stay warm across jobs, so execution is fast. Read the mode's name narrowly: the engine process itself is **not** namespace-isolated here — a qadam action still runs with the worker's own privileges inside a plain fork. Only Code steps are V8-confined, and that boundary is pinned by `execution-modes.e2e.test.ts` (#712).

- **V8 guarantees:** user code cannot touch `require`, the filesystem, or other steps' memory.
- **V8 does not:** protect isolates from each other if the host Node process itself is compromised.

### `isolate` binary — `SANDBOX_PROCESS`, `SANDBOX_CODE_AND_PROCESS`

The engine runs inside [ioi/isolate](https://github.com/ioi/isolate), which creates fresh PID, mount, user, and UTS namespaces per run and mounts the engine and code artifacts read-only. The cost: cold boot per run (not reusable), and the worker container must hold `CAP_SYS_ADMIN` — `--privileged` in Docker, `securityContext.privileged: true` in Kubernetes.

The Code step differs between the two isolate modes. `SANDBOX_PROCESS` runs Code steps in the same namespace-isolated box as the engine, so arbitrary `npm` packages are safe there because filesystem and process state are scoped to the box. `SANDBOX_CODE_AND_PROCESS` adds the V8 layer on top: Code steps get no `require`, filesystem or npm — the box protects the host from the engine, V8 protects the engine from the Code step.

### Running an isolate mode with Docker Compose

The bundled `docker-compose.yml` grants the worker no extra capabilities, because `UNSANDBOXED` and `SANDBOX_CODE_ONLY` do not need them. To run an isolate mode, set it in `.env` and select the opt-in override that adds `CAP_SYS_ADMIN` (and `CAP_NET_ADMIN` when `AP_NETWORK_MODE=STRICT`, which the egress lockdown needs) and lifts the seccomp/AppArmor confinement:

```dotenv
AP_EXECUTION_MODE=SANDBOX_PROCESS
```

The installer fetches `docker-compose.sandboxed.yml` and selects it for you when you opt in once with `QADAM_FLOW_SANDBOXED=yes`:

```bash
curl -fsSL https://flow.aiqadam.org/run.sh | QADAM_FLOW_SANDBOXED=yes sh
```

It writes `COMPOSE_FILE=docker-compose.yml:docker-compose.sandboxed.yml` into `.env`, so the capabilities survive a later plain `docker compose up -d` and an upgrade that re-runs `run.sh` without the flag. To revoke the opt-in, run the installer once with `QADAM_FLOW_SANDBOXED=no`, which removes that line again; leaving the variable unset keeps an existing choice. If you applied the override by hand as `docker-compose.override.yml` instead, `no` does not touch it — delete that file yourself.

If you manage the compose files by hand instead, copy the override into place — Compose merges `docker-compose.override.yml` automatically, so a later `run.sh` upgrade keeps it:

```bash
cp docker-compose.sandboxed.yml docker-compose.override.yml
docker compose up -d
```

If you installed by downloading only `docker-compose.yml`, fetch the override beside it first:

```bash
curl -fsSL https://raw.githubusercontent.com/aiqadam/qadam-flow/main/docker-compose.sandboxed.yml -o docker-compose.sandboxed.yml
```

<Warning>
This gives the worker `CAP_SYS_ADMIN` and `CAP_NET_ADMIN`, container-escape-grade capabilities. A kernel or runtime escape from a privileged worker reaches the host and everything else on it, as in the Kubernetes example above. Run it on a dedicated node, or prefer `SANDBOX_CODE_ONLY`.
</Warning>

The worker probes the isolate sandbox once at startup. If the capabilities are missing — for example, an isolate mode was set without the override — it refuses to start with an actionable message instead of failing every job mid-run.

## Network Isolation

Execution mode decides *how* user code runs; `AP_NETWORK_MODE` decides *what it can reach*. See [Network Security](./network-security) for the SSRF guard, egress proxy, and iptables lockdown that layer on top of every sandbox mode.
