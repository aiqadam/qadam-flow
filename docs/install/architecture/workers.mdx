The **worker** is the container that actually runs flows. It pulls jobs from Redis, executes each one inside a sandbox, and streams results back to the app. This page is about operating it: how many to run, how to size them, and what happens when one dies mid-flow.

## What a Worker Does

Each worker pulls jobs off the BullMQ queue in Redis, hands them to a sandboxed engine process, and posts progress and results back to the app over HTTP. Workers are **stateless** — they hold no per-flow memory, which is what makes horizontal scaling and crash recovery straightforward.

## Scaling

There are two independent knobs:

- **Replicas** — scale horizontally. Workers are stateless, so adding replicas is safe behind any orchestrator (Docker Compose, Kubernetes, Nomad). The default Docker Compose setup starts 5 replicas.
- **`AP_WORKER_CONCURRENCY`** — concurrent jobs per replica. Default `5`. Each concurrent job uses one sandbox instance, so this also sets the peak sandbox count per worker.

Size replicas for throughput, and concurrency for how much a single replica can chew on. If flows are CPU-bound, lower concurrency and add replicas. If flows are I/O-bound (most automation workloads), raise concurrency before adding replicas.

See [Hardware Requirements](../configuration/hardware) for per-replica memory and CPU sizing.

<Tip>
In `UNSANDBOXED` and `SANDBOX_CODE_ONLY` modes, sandboxes stay warm across jobs, so steady-state execution is fast. `SANDBOX_PROCESS` spins up a fresh sandbox per run, which trades latency for kernel-level isolation.
</Tip>

In those two modes, while `AP_REUSE_SANDBOX` is unset or `true`, each worker also starts one engine per concurrency slot when it starts, so the first job on each slot doesn't pay the engine's start-up. A reconnect keeps the engines it already has. A slot whose engine was replaced, because the app's worker settings changed or a job was given up, starts its next engine on its next job. An engine holds about 100 MB. A busy worker reaches the same number of engines anyway, so the peak doesn't change, but it is reached at boot rather than under load. The default Docker Compose setup (5 replicas × concurrency 5) holds about 2.5 GB of engines right after it starts. On a host that can't hold that at boot, set `AP_WORKER_PREWARM_ENGINES=false` to start engines on first use instead. The variable accepts only `true` or `false`.
## Restarts and Deploys

- **The app restarts.** Workers reconnect on their own. Jobs that were running keep running, confirm they still own their job as soon as the connection is back, and report their result over it. Warm sandboxes stay warm, unless the restarted app sends different worker settings. Then an idle sandbox is replaced at once, and a busy one after its job.
- **The app is down for longer.** A worker renews each running job's lock every 30 seconds, and the lock lasts 120 seconds. After 90 seconds without a renewal, the worker stops that job and does not report it, because the app may have handed the job to another worker by then. The app runs the job again once the lock expires. Progress updates have a shorter limit: the engine stops waiting for one after 60 seconds, so an outage of more than a minute can still fail a run that reports progress during it.
- **A worker stops.** On `SIGTERM`, for example when `docker compose up -d` replaces the image, the worker takes no new jobs and waits up to `AP_WORKER_SHUTDOWN_GRACE_SECONDS` (default `60`, at most `3600`) for its running jobs to finish. A job still running after that is abandoned, and the worker logs how many as `abandonedJobs`. The app's stalled-job check puts an abandoned job back in the queue once its lock expires, up to about two and a half minutes later, and another worker runs it again.
- **Give the worker time to drain.** The worker exits by itself at most 15 seconds after the grace. Your orchestrator must wait longer than that before it kills the container. The bundled `docker-compose.yml` sets `stop_grace_period: 90s` on the worker, for the default grace of 60 seconds; raise the two together. Docker's own default is 10 seconds. On Kubernetes, set `terminationGracePeriodSeconds` above the grace plus 15 seconds, or lower the grace to fit.
- **Existing installs.** `docker compose pull` updates the image, not your `docker-compose.yml`. If you installed with the install script, run it again: it refreshes the compose file and keeps your `.env`. Or add `stop_grace_period: 90s` to the worker service yourself. A git checkout gets the new file with `git pull`, which `tools/update.sh` runs.

## Failure Behaviour

If a worker crashes, is evicted, or loses its Redis lease mid-run, BullMQ requeues the job and another worker picks it up. The engine's durable-execution layer replays already-completed steps from persisted state rather than re-running them, so side effects are not duplicated. This means a worker restart or OOM kill during a flow is survivable — you do not need to drain traffic before rolling workers.

See [Durable Execution](./durable-execution) for exactly what is persisted and how replay works.

## Sandbox & Network Isolation

How flows are isolated from the worker container and the outside world is two independent choices:

- [**Sandboxing**](./sandboxing) — `AP_EXECUTION_MODE` decides how user code is isolated from the host kernel. This is the most important security decision for multi-tenant deployments.
- [**Network Security**](./network-security) — `AP_NETWORK_MODE` decides what the sandbox is allowed to reach on the network.
