## How this page is enforced

<Note>
This section is for maintainers cutting a release. If you are upgrading an install, skip to the version list below.
</Note>

This page is not maintained by convention — a CI job refuses to publish a release without it.

**Why.** [PR #210](https://github.com/aiqadam/qadam-flow/pull/210) removed the `WORKER_AND_APP` launch mode and made `AP_CONTAINER_TYPE` required. Any all-in-one container install refuses to start after that ships, and there is no automated migration from the embedded PGLite database to PostgreSQL, so recovery is manual. The change *is* written up below — but only because a person noticed it needed to be. Nothing mechanical would have stopped the release. Since `:latest` is published solely by `release.yml` on a tag push (merges to `main` publish `:main` and `:sha-…` only), the tag is the last moment at which a check can stop an undocumented breaking change from reaching users, so that is where the check lives.

**What it does.** On a `v*` tag push, `tools/ci/check-breaking-change-changelog.sh` walks every commit from the previous non-prerelease tag up to the tag being released. If any of them declares a breaking change — a Conventional Commits `type!:` subject, or a `BREAKING CHANGE:` footer — then this file must have been modified somewhere in that range **and** must contain a non-empty `## <version>` section for the version being released. In practice that means renaming the `## Unreleased` heading below to the version number as part of cutting the release.

**What it cannot catch.** It reads declarations, not behaviour. A breaking change that nobody marked with `!` or a `BREAKING CHANGE:` footer passes it, as does an entry whose content is useless. It raises the floor; it does not replace review.

**When it cannot measure, it fails.** A shallow checkout, a missing tag, an empty commit range or a missing changelog file all exit with `UNKNOWN` and fail the release rather than reporting "no breaking changes found". An empty measurement is never rendered as a pass.

**Overriding it.** If a `!` commit genuinely needs no entry here, the preferred fix is a `Breaking-Change-Exempt: <reason>` trailer on that commit. At release time, when rewriting the commit is no longer an option, re-cut the tag as an *annotated* tag whose message contains:

```
Release-Gate-Override: <why this release needs no changelog entry>
```

for example:

```bash
git tag -d v1.2.0
git tag -a v1.2.0 -m 'Release-Gate-Override: entry lands in #999, shipping the hotfix first'
git push -f origin v1.2.0
```

The gate then passes and prints the tagger's name, email and reason into the job log and the run summary. The reason is stored in the tag object, so `git show v1.2.0` shows it forever. This is deliberately a little more work than writing the changelog entry, and deliberately impossible to do invisibly — a lightweight tag cannot carry an override. Do not delete the check instead; the whole reason it exists is that the previous control was somebody remembering.

## Unreleased

### What has changed?

#### JWTs are now issued as `qadam-flow` — and no action is required

The `iss` claim on every token the platform mints changes from the inherited `activepieces` to `qadam-flow`. This includes the long-lived `AP_WORKER_TOKEN` that `docker-entrypoint.sh` and `qadam-flow token` generate.

- **No action is required, and nothing needs regenerating.** The verifier accepts both issuers. On the bundled compose install `AP_WORKER_TOKEN` is minted by the entrypoint at container start and never written to disk, so workers re-mint under the new issuer on their own the first time they restart.
- **A hand-set `AP_WORKER_TOKEN` keeps working indefinitely.** `qadam-flow token` mints with a 100-year expiry, so if you set the variable yourself there is nothing to do — the legacy issuer stays accepted.
- **Existing user sessions keep working** (7-day expiry), as do engine tokens already embedded in queued jobs (`AP_EXECUTION_DATA_RETENTION_DAYS`, default 30 days). Nobody is signed out and no queued run fails authentication.
- **Upgrade the `APP` container before the workers.** A new-image worker mints `qadam-flow`, which an APP container still on the old image will not accept. `docker compose up -d` recreates both together so the window is momentary, but on a multi-server or staged rollout do the API first.
- **Rolling back is not free.** Any session or queued engine token minted while the new version was running carries `iss: qadam-flow`, which the old verifier rejects: users are signed out and in-flight runs fail authentication until those tokens age out. Workers self-heal on restart.
- Newly minted tokens carry `iss: qadam-flow`. If you have external tooling that inspects the claim — a log pipeline, an API gateway, a monitoring rule — it must accept both.

#### `AP_CONTAINER_TYPE` is now required, and `WORKER_AND_APP` has been removed

The image no longer runs a process supervisor (PM2) of its own. Docker supervises one Node process per container, so a crash exits the container and shows up in `docker ps` and `docker events` instead of being restarted in place behind an `Up` status.

- **`AP_CONTAINER_TYPE` must be set to `APP` or `WORKER`.** There is no default. Previously an unset value meant `WORKER_AND_APP`.
- **`WORKER_AND_APP` is rejected.** The entrypoint exits with an explanatory error rather than falling back to a partial stack — a container that serves HTTP with no worker behind it is exactly the failure this change exists to stop.
- **`AP_PM2_INSTANCES` no longer does anything.** It is still read, only to warn when it is set above `1`. To use more than one CPU for the API, run several `APP` containers behind a load balancer.
- **The server enforces this too, not just the entrypoint.** `WORKER_AND_APP` is gone from the `ContainerType` enum, and the API and worker processes now fail on first read of `AP_CONTAINER_TYPE` when it is unset, blank, or anything other than `APP` or `WORKER` (case-sensitive; the Node processes tolerate surrounding whitespace and a trailing carriage return, but the container entrypoint does not — a CRLF `.env` still fails there). This only affects running the Node processes directly — every Docker install already goes through the entrypoint check above. Previously the server carried its own `WORKER_AND_APP` default, so a bare process silently started both subsystems while the documentation said there was no default; a blank or misspelled value was worse still, matching neither branch and producing an API that bound its port with no routes and no database while `/api/v1/health` answered `200 Healthy`.

**If you use the bundled `docker-compose.yml` or the `run.sh` installer, no action is required** — both already set `AP_CONTAINER_TYPE` explicitly on each service.

**If you run the all-in-one container** (`docker run … ghcr.io/aiqadam/qadam-flow:latest` with `AP_DB_TYPE=PGLITE` and `AP_REDIS_TYPE=MEMORY`), do not pull a newer image: it will refuse to start. There is no automated migration from the embedded PGLite database to PostgreSQL, so stay on your current image tag until you have moved your flows by hand, or rebuild them in a fresh compose install. Note that this mode has in fact been running **without a worker at all** — the worker never received a token and the in-container supervisor stopped it after a few restarts — so flows in such an install have not been executing.

#### Environment variables are migrating from `AP_` to `QF_`
This is the start of a multi-release migration — **no action is required**, every `AP_*` variable keeps working exactly as before.

- Every environment variable that was previously read as `AP_<NAME>` (e.g. `AP_EXECUTION_DATA_RETENTION_DAYS`, `AP_TELEMETRY_ENABLED`, `AP_WEBHOOK_TIMEOUT_SECONDS`) can now also be set as `QF_<NAME>` (e.g. `QF_TELEMETRY_ENABLED`) **when it reaches the Node server or worker process** — directly, via `.env`, or via `docker run -e`.
- If both `QF_<NAME>` and `AP_<NAME>` are set, `QF_<NAME>` wins. An empty `QF_<NAME>` (e.g. `""`) is treated as unset and does not override a valid `AP_<NAME>`.
- Setting only the old `AP_<NAME>` still works and behaves identically, but logs a one-time startup warning telling you to rename it to `QF_<NAME>` — **except for the ~10 names that `docker-entrypoint.sh`/`docker-compose.yml` read in the shell** (`AP_CONTAINER_TYPE`, `AP_PORT`, `AP_PM2_INSTANCES` — accepted and ignored, see above — `AP_JWT_SECRET`, `AP_WORKER_TOKEN`, `AP_POSTGRES_DATABASE`, `AP_POSTGRES_PASSWORD`, `AP_POSTGRES_USERNAME`, `AP_QADAMS_SYNC_MODE`, `AP_WORKER_API_URL`) plus the already-deprecated `AP_*_PIECES` names. Those are exempt from the warning because renaming them today wouldn't do anything for the shell scripts that read them (see below) — warning about them would just tell every stock Docker install to make a change that breaks it.
- `AP_ENVIRONMENT` (and its `QF_ENVIRONMENT` alias) still only accepts `prod` / `dev` / `test` — only the variable name is changing, not its accepted values.
- **The bundled `docker-compose.yml`, `docker-entrypoint.sh`, and the `run.sh` install script still require the `AP_*` names and are not part of this alias.** Those scripts read the variables in the shell — before Node (and this alias layer) ever starts — to do things like interpolate `${AP_POSTGRES_PASSWORD}` into Postgres's own config and decide which process (`APP`/`WORKER`) to launch via `AP_CONTAINER_TYPE`. Setting only `QF_POSTGRES_PASSWORD` or `QF_CONTAINER_TYPE` today does **not** reach those scripts and can leave Postgres with an empty password or start the wrong container topology. Keep using `AP_*` for anything consumed by `docker-compose.yml` / `docker-entrypoint.sh` / `run.sh` until a follow-up migrates those in lockstep.

#### PGLite has been removed — `AP_DB_TYPE=PGLITE` is no longer accepted

PGLite existed only to support the one-container "quick look" install, and that install mode was already removed above (`WORKER_AND_APP`) — it turned out to be running with no worker at all, so nothing that depended on PGLite was actually executing flows. With that install gone, PGLite has no remaining reason to exist and has been dropped entirely: the dependency, the connection code, and the `PGLITE` value of `AP_DB_TYPE` are all gone from the image.

- **`AP_DB_TYPE` now accepts only `POSTGRES`.** Setting it to `PGLITE` (or the older, already-deprecated `SQLITE3`) fails at startup with an explanatory error instead of falling back to anything.
- **There is no automated migration from a PGLite data directory to PostgreSQL.** If you have data sitting under `AP_CONFIG_PATH/pglite`, there is no export tool that moves it into a Postgres install.

**If you already run `AP_DB_TYPE=POSTGRES`** (the bundled `docker-compose.yml` and `run.sh` installer both do), no action is required.

**If you still have `AP_DB_TYPE=PGLITE` set anywhere** — including the all-in-one container mode described above — do not pull a newer image. Stay on the image tag you are running now until you have moved your flows to Postgres by hand, or rebuild them in a fresh compose install.

#### The image no longer bakes in an embedded Redis (`AP_REDIS_TYPE=MEMORY`)

`redis-memory-server` compiled a Redis binary into the image so the application could run its own
in-process Redis. That existed for the all-in-one container, which was removed above — it now refuses
to start — and every supported install path runs Redis as its own service (`run.sh` and the bundled
`docker-compose.yml` both do).

- **`AP_REDIS_TYPE=STANDALONE` with a real Redis is the supported configuration.** The bundled
  `docker-compose.yml` and `run.sh` already set it, so **no action is required** for either.
- **If you are on the embedded Redis**, the container will now download and compile Redis on first
  start, which needs network access and a build toolchain. Run Redis as its own service instead.
  Note there are **two** ways to be in this mode: `AP_REDIS_TYPE=MEMORY`, and the legacy
  `AP_QUEUE_MODE=MEMORY`, which is still silently mapped onto it — so check both.

#### The language picker now offers only English, Russian, Uzbek and Kazakh

Nine UI locales have been removed: Dutch, German, French, Spanish, Japanese, Portuguese, Arabic, Simplified Chinese and Traditional Chinese. The product's language coverage now follows the Organization of Turkic States, plus Russian as a regional lingua franca and English as the source language.

- **`LocalesEnum` in `@aiqadam/shared` no longer contains those nine members.** Anything importing them fails to compile. This is why the change is marked breaking even though it is user-facing rather than API-facing for most installs.
- **A user whose interface was one of those languages now sees English.** No data is affected — only the rendered UI text. They can still pick Russian, Uzbek or Kazakh from the language menu.
- **A browser set to a removed language falls back to English** rather than being offered a partially translated interface.
- **Qadam translation files are unchanged on disk, but nine of them stop being read.** `packages/qadams/**/src/i18n/*.json` is untouched, however the framework decides which of those files to load by iterating `LocalesEnum`. So the 1,662 files for the removed languages become dead weight, and **`GET /v1/qadams?locale=de` still returns `200` while silently serving English** action and trigger names where it previously served German. The `locale` query parameter is a free-form string, so nothing rejects the request — it just stops translating.
- **The `ap_research_pieces` MCP tool now rejects a removed locale outright.** Unlike the REST route, that tool validates `locale` against `LocalesEnum`, so an MCP client passing `locale: "de"` gets a schema validation error instead of degrading to English. If you drive this install over MCP with an explicit locale, update those calls.

**If you rely on one of the removed interface languages,** stay on your current image tag, or switch the affected users to English, Russian, Uzbek or Kazakh. If you need one of them restored, open an issue: the translation files remain in git history and can be brought back.

### Do you need to take action?
- No, if you already run against PostgreSQL. Renaming `AP_*` to `QF_*` is optional during the deprecation window described above; `AP_*` support will be removed in a future release, announced here with advance notice.
- Yes, if `AP_DB_TYPE=PGLITE` or `AP_DB_TYPE=SQLITE3` is set anywhere in your configuration: stay on your current image tag, or move to Postgres and rebuild in a fresh install — there is no automated path between the two.
- Yes, if `AP_REDIS_TYPE=MEMORY` **or** the legacy `AP_QUEUE_MODE=MEMORY` is set: switch to `STANDALONE` and run Redis as its own service. The bundled `docker-compose.yml` and `run.sh` already do this, so a stock install needs nothing.

- Only if your users read the interface in Dutch, German, French, Spanish, Japanese, Portuguese, Arabic or Chinese: those interface languages are gone and those users will see English. Nothing needs migrating; it is a display change.


## 0.84.0

### What has changed?

#### Flow Run Log Size Enforcement
This is an important behavior change in how flow run logs are stored and capped, but **no action is required** — the existing default (`AP_MAX_FLOW_RUN_LOG_SIZE_MB=50`) is preserved.

- Large step outputs are now offloaded to object storage instead of sitting inline in worker memory, controlled by the new `AP_FLOW_RUN_LOG_SLICE_THRESHOLD_KB` env var (default `32`).
- Large step input values are replaced with a `(truncated, original size <N>)` placeholder in the log via the new `AP_FLOW_RUN_LOG_INPUT_TRUNCATE_THRESHOLD_KB` env var (default `2`). The step still receives the full value at runtime.
- Runs whose combined step inputs and outputs exceed `AP_MAX_FLOW_RUN_LOG_SIZE_MB` now terminate with the new `LOG_SIZE_EXCEEDED` status instead of silently trimming inputs. Offloaded outputs still count their original size against the cap.
- See [Technical Limits → Files & flow run logs](/flows/known-limits#files-flow-run-logs) for the full behavior, environment variables, and defaults.
- Embedding now requires setting allowed embed origins, which means only the domains listed in the field can embed the app (wildcards are supported). There is also a new env variable `AP_ALLOWED_EMBED_ORIGINS` for setting pre-allowed origins, and a new endpoint for adding these origins — [check docs](/endpoints/embedding/add-allowed-embed-origins).

### Do you need to take action?
- **Embedding** — if you are embedding your self-hosted Qadam Flow somewhere make sure it's on the allow list

## 0.82.0

### What has changed?

#### Qadam Versions Are Now Pinned
- Qadam versions are no longer stored with wildcards (`~1.2.0`, `^1.2.0`). All qadam steps now use exact versions (e.g. `1.2.0`).
- A migration automatically strips wildcard prefixes from all existing flow versions on upgrade.
- The `LOCK_AND_PUBLISH` operation no longer resolves qadam versions at publish time — steps run with the exact version stored in the flow.
- A new **version switcher** UI in the builder lets users upgrade or downgrade qadam versions manually.

#### REST API
- `ADD_ACTION`, `UPDATE_ACTION`, and `UPDATE_TRIGGER` now strip wildcard prefixes (`~`, `^`) from `pieceVersion` before saving. If you were relying on wildcard versions to auto-resolve on publish, your steps will now be pinned to the base version (e.g. `~1.2.0` becomes `1.2.0`).
- `LOCK_AND_PUBLISH` no longer modifies `pieceVersion` on any step. The version in the draft is the version that will run.
- A new endpoint `GET /v1/qadams/:name/versions` is available to list all versions of a qadam, useful for building custom version selection.

#### Concurrent Jobs Env Var Renamed
- `AP_MAX_CONCURRENT_JOBS_PER_PROJECT` → `AP_DEFAULT_CONCURRENT_JOBS_LIMIT`. Default drops from `100` to `5`.

#### Outbound HTTP is SSRF-filtered
- Server-side HTTP (OAuth, Vault, Conjur, event destinations, on-call pager, MCP validator) now blocks private, loopback, and cloud-metadata IPs. Reach internal hosts by adding their IP/CIDR to `AP_SSRF_ALLOW_LIST`.

### Do you need to take action?
- **Pinned qadam versions** — if you create or update flows via the REST API with wildcard versions (`~` or `^`), switch to exact versions; wildcards are silently stripped. If your publish flow relied on `LOCK_AND_PUBLISH` resolving wildcards, set the exact version on each step before publishing. Use `GET /v1/qadams/:name/versions` to list available versions.
- **Concurrent jobs** — rename `AP_MAX_CONCURRENT_JOBS_PER_PROJECT` to `AP_DEFAULT_CONCURRENT_JOBS_LIMIT`. To keep the old cap, set `AP_DEFAULT_CONCURRENT_JOBS_LIMIT=100`.
- **SSRF filter** — if you self-host Vault, Conjur, an OAuth2 token endpoint, or any internal webhook on a private IP, set `AP_SSRF_ALLOW_LIST` (comma-separated IPs or CIDRs, e.g. `10.0.5.12,192.168.10.0/24`) before upgrading.


## 0.80.0

### What has changed?

#### Infrastructure
- A new environment variable `AP_MAX_WEBHOOK_PAYLOAD_SIZE_MB` has been introduced to control the maximum allowed webhook payload size. The default is `25` MB. Webhooks exceeding this limit will be rejected with a `413 Request Too Long` response.
- Nginx has been removed from the Docker image. Fastify now serves both the API and the React frontend directly. All API routes are now under the `/api` prefix natively. If you were using `/v1/health` as a health check endpoint (e.g. in Kubernetes probes or load balancer checks), update it to `/api/v1/health`.
- Secret managers has been refactored, the version in **0.79.0** no longer is supported, it was not used by anyone but it's worth to mention to upgrade to **0.80.0** before considering using the feature

#### API
- A new `UPDATE_SAMPLE_DATA_INFO` flow operation has been introduced to handle sample data updates independently.
- `UPDATE_ACTION` and `UPDATE_TRIGGER` no longer accept or apply changes to `sampleData` in step settings. Any `sampleData` fields sent in these requests will be ignored and the existing sample data will be preserved.
- A new required `lastUpdatedDate` field has been added to all actions and triggers, tracked automatically by the server. It is not accepted in `UPDATE_ACTION` or `UPDATE_TRIGGER` requests.


### Do you need to take action?
- If you want to restrict webhook payload sizes below the new `25` MB default, set `AP_MAX_WEBHOOK_PAYLOAD_SIZE_MB` to your desired limit.
- If you are using the API to update sample data on steps via `UPDATE_ACTION` or `UPDATE_TRIGGER`, switch to the new `UPDATE_SAMPLE_DATA_INFO` operation instead.
- If you have custom health checks pointing to `/v1/health`, update them to `/api/v1/health`.

- If you are using `AP_CODE_SANDBOX_TYPE` to `V8_ISOLATE`, you should switch to `AP_EXECUTION_MODE` to `SANDBOX_CODE_ONLY`
- If you are using `AP_SANDBOX_RUN_TIME_SECONDS` to set the sandbox run time limit, you should switch to `AP_FLOW_TIMEOUT_SECONDS`

## 0.28.0

### What has changed?

- **Project Members:**
    - The `EXTERNAL_CUSTOMER` role has been deprecated and replaced with the `OPERATOR` role. Please check the permissions page for more details.
    - All pending invitations will be removed.
    - The User Invitation entity has been introduced to send invitations. You can still use the Project Member API to add roles for the user, but it requires the user to exist. If you want to send an email, use the User Invitation, and later a record in the project member will be created after the user accepts and registers an account.
- **Authentication:**
    - The `SIGN_UP_ENABLED` environment variable, which allowed multiple users to sign up for different platforms/projects, has been removed. It has been replaced with inviting users to the same platform/project. All old users should continue to work normally.

### When is action necessary?

- **Project Members:**

If you use the embedding SDK or the create project member API with the `EXTERNAL_CUSTOMER` role, you should start using the `OPERATOR` role instead.

- **Authentication:**

Multiple platforms/projects are no longer supported in the community edition. Technically, everything is still there, but you have to hack using the API as the authentication system has now changed. If you have already created the users/platforms, they should continue to work, and no action is required.
