# Qadam Pin Moves

## Summary
ADR-0003's "Unavailable version" and "Versions that were never published" (#808, first slice). A step stores the exact version of the qadam it was built with. When the instance cannot have that version (the #411 / #422 / #432 population: pins to builds that were never published, so neither the store nor the image holds them), the step is **moved** to the image's version, and only when all of these hold: the image's version is inside the pin's caret range (ADR-0001, prereleases counted, ADR-0004), the props are compatible where metadata for the pinned version exists, and the target loaded successfully. The move is one audit record plus the rewrite of the step's pin in the flow version, committed together, and a platform admin can revert it by restoring the old pin in a draft. A step that is not moved stays as it is, with the reason; no flow is ever disabled (#435). The marking in the builder, MCP and runs ("update this step"), the start-up pass, the import path and replacing the v31 heal are later slices.

## Domain Terms
- **Pin move** — the audited rewrite of one step's pinned version; the row in `qadam_pin_move`.
- **Run-time net** — the in-memory stand-in that still runs a stale release pin on the image's build inside its caret range (`checkNet`: API `findBundledFallback`, engine `qadamPinFallback`): loud, read-only, no audit and no revert, a snapshot pin never gets one and a release pin never gets a snapshot build. It stays until the move covers every path that can notice a stale pin (start-up, import); deleting it makes the remaining unavailable pins fail with the pin named.
- **Held** — a step whose move a person reverted. The same flow, step, qadam and version are not moved again.

## Behaviour
- **When.** `LOCK_AND_PUBLISH` only (cause `PUBLISH`), on the draft before it is locked, so the draft becomes the published version through the normal publish and workers, trigger sources and polling jobs see a new version id as for any publish. A locked version is never moved (a publish of an already locked latest version moves nothing). Enabling a flow does not move pins: published pins stay with the run-time nets and the v31 heal for now.
- **Which pins.** PIECE steps and triggers with an exact pin (`x.y.z` or `x.y.z-main.<n>`) that `qadamMetadataService.isPinAvailable` answers `false` for (not in the registry and not in the version store). A lookup that errors is not "unavailable". Range pins (`^`, `~`) resolve against what the instance holds and are left alone. Agent-tool pins are not steps and are not rewritten.
- **The image.** The bundled build of the same name that passes the platform and release filters. Custom qadams have none, so their steps are never moved.
- **The checks, in order.** Caret range → props → load; the first failure is the reason. Props: a release's metadata comes from the catalogue and a snapshot's from the store (`snapshotExportSources`). A catalogue entry the reader could not parse counts as unknown (`skippedEntries`), not as absent. A catalogue that was read and has an entry runs the props check; one that was read and has **no** entry is the never-published population (ADR-0003), which moves with `propsCheck = 'not-checked-no-metadata'`; a catalogue or store that cannot be read is *unknown* and the step stays (`props-unverifiable`). The catalogue's address answers 404 until #778 publishes it, so on a real instance published pins stay put until then: the intended fail-closed behaviour. A snapshot pin without its own metadata is not moved (ADR-0004). Load: the loaded bundle list holds only builds whose module loaded (the manifest writer refuses a partial catalogue, the scan skips a failed load), so "the image ships it" is the load check, and it catches a bundle that cannot be loaded (the prototype's `crypto`). It does not run an action: a target that loads but fails at run time (activepieces#15957) is what the revert is for.
- **Locked versions are never rewritten.** A worker caches a locked version by its id and a trigger source (or polling job) keeps the pins and version id it was registered with, so neither a move nor a revert touches a locked version or `publishedVersionId`.
- **The write.** One transaction: the flow-version row is locked, each planned step is rewritten only if it is still at the version the plan saw, the audit rows are inserted. The publish that follows invalidates the flow-execution cache.
- **Revert.** `POST /v1/qadam-pin-moves/:id/revert` (platform admin). It restores the old pin in the flow's DRAFT version(s) where the step is still at `toVersion`; when the flow has no draft (the publish locked it) it makes one from the published version, the way an edit does (`updatedBy` is the reverting user), with the old pin restored, and marks the record `REVERTED`. The response carries `publishRequired`: true while the published version still holds the moved pin, which keeps running until the restored draft is published. When no draft (or, with no draft, the published version) carries the moved pin it is refused with `ErrorCode.VALIDATION` (HTTP 409). **Hold:** a reverted record holds the step whenever it later sits on that `fromVersion` again in the same flow, not only in the draft the revert restored. **Serialized:** two reverts of one flow (a transaction-level advisory lock on the flow); a revert against a publish (the drafts are read `FOR NO KEY UPDATE`, the lock a publish takes on the version it publishes, and the flow row is read after them so a publish that committed first is seen; the flow row is never locked first, which would deadlock with a publish). **Not serialized:** a concurrent *edit* creating a draft at the same moment as a revert (two concurrent edits can already do that).

## Not done yet (#808)
Moving or reverting a **published** version: it needs a design that creates a new locked version and re-registers the trigger source (including polling and schedule jobs keyed by version id) under the flow-status-change lock, with a failure policy that never leaves a flow disabled (#435). Until then published pins stay with the run-time nets and the v31 heal, and enabling a flow does not move pins. Also: the "update this step" / "version unavailable" marking in the builder, MCP (`ap_flow_structure`, `ap_validate_flow`) and runs, with project-level read and revert; the start-up pass and the import path; replacing the one-shot v31 heal (#474, still crosses the caret range) and the per-lookup net; removing the #843 stopgaps.

**Known limits.** A draft open in a builder with a stale copy can send the old pin back after a revert (the hold applies when the step sits on `fromVersion` again, which a stale copy does). Publish re-reads the version under `FOR NO KEY UPDATE` (which does not block `flow_run` inserts), runs the #436 gate on it before locking and throws when it is gone; if that transaction fails after the trigger source was disabled, the previous published version's trigger source is enabled again, under the `flow-status-change-<id>` lock and from a fresh read, only when the flow is still ENABLED on that previous version and no trigger source is registered, so a flow a person disabled meanwhile, or another publish, is left alone (the disable stays before the transaction: moving it would change which version its hook sees). An edit landing in that window is covered by the gate, not by a test (no seam). The catalogue index is read once per move call, and not at all when the image ships no build.
