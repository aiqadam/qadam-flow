# Flow Runs Module

## Summary
Flow Runs records every execution of a flow, tracking its full lifecycle from queuing through completion or failure. It stores compressed execution logs for step-by-step inspection, supports pause-and-resume for delay and webhook-based waits, provides retry strategies for recovering from failures, and emits WebSocket events to the frontend plus in-process application events (consumed only by the badge service).

## Domain Terms
- **FlowRun**: A single execution instance of a specific flow version, from trigger to terminal state.
- **FlowRunStatus**: One of 12 states — 3 non-terminal (QUEUED, RUNNING, PAUSED) and 9 terminal (SUCCEEDED, FAILED, TIMEOUT, CANCELED, QUOTA_EXCEEDED, MEMORY_LIMIT_EXCEEDED, INTERNAL_ERROR, LOG_SIZE_EXCEEDED, plus PAUSED terminal via delay).
- **LogsFile**: Zstd-compressed File entity (type FLOW_RUN_LOG) storing the full `FlowExecutorContext` after execution.
- **Waitpoint**: Row in the `waitpoint` table representing one paused step on a run. Fields: `type` (DELAY|WEBHOOK), `version` (V0|V1 — V1 is the current API), `status` (PENDING|COMPLETED), `stepName`, `resumeDateTime`, `responseToSend`, `resumePayload`, `workerHandlerId`, `httpRequestId`. Unique on `(flow_run_id, step_name)`.
- **PauseMetadata** *(legacy/V0)*: JSONB column on `flow_run` distinguishing DELAY vs WEBHOOK pauses. Deprecated 2026-04-13 (0.82.0) — nothing writes it any more, so a shim-era-or-later PAUSED run always has it NULL; only read as one of three required conditions for the V0 no-waitpoint legacy resume branch (see "Pause & Resume" below). V1 runs store this information on the `waitpoint` row instead.
- **Retry Strategy**: FROM_FAILED_STEP (resume from exact failure point, keeping prior outputs — but if the trigger itself failed, restart with BEGIN + `executeTrigger: true` since there is nothing to resume from) or ON_LATEST_VERSION (fresh run on current published version, re-runs the trigger when the previous attempt's trigger failed).
- **ResumeReason**: `WAITPOINT` | `RETRY`. Set on every `ExecutionType.RESUME` engine operation and threaded through `ExecuteFlowJobData`. Determines whether the engine restores FAILED steps from the journal — waitpoint resumes preserve them, retry resumes drop them so the failed step re-executes. The two resume paths share the same `ExecutionType`, so this field is the only discriminator.
- **Subflow**: A child run linked via `parentRunId`, created when a flow calls another flow as a step.
- **failedStep**: JSONB snapshot of `{ name, displayName, message? }` for the step that caused failure. Enables filtered retries, the runs-table error-message search, the failure email's "Reason" line, and the builder's jump-to-failed-step affordance. `message` is truncated via `truncateString` from `@aiqadam/shared` before being persisted, and the engine populates `failedStep` for every status in `FAILED_STATES` (FAILED, TIMEOUT, INTERNAL_ERROR, QUOTA_EXCEEDED, MEMORY_LIMIT_EXCEEDED) — not just `FAILED`.
- **FriendlyPieceError**: Structured error shape (`__apErrorVersion`, `message`, optional `status`, `errorName`, `requestBody`, `responseBody`, `apiMessage`, `raw`) produced by `formatPieceError` in the engine when a piece step throws (replacing the old `util.inspect` dump). The builder parses it with `tryParseFriendlyPieceError` and renders a `FriendlyErrorView` card — plain-language headline, the service's message, a "Copy Error for AI" button, and a "Technical Details" disclosure holding the `raw` dump — in both the test panel and the run-details output view.

## Entity

**FlowRun**: id, projectId, flowId, flowVersionId, environment (PRODUCTION/TESTING), logsFileId (nullable FK to File), parentRunId (nullable, self-reference for subflows), failParentOnFailure (default true), parentWaitpointId (nullable, the exact waitpoint a subflow child's failure is allowed to complete — see the `WEBHOOK` waitpoint bullet below), parentSlotId (nullable, the join slot a `callFlowForEach` child answers — see the join waitpoint bullet below; creation-time only, in `RUNS_METADATA_UPSERT_KEYS`), dispatchMode (nullable: QUEUE/INLINE), status, tags[] (nullable), startTime, triggeredBy (nullable FK to User), finishTime, pauseMetadata (JSONB), failedStep (JSONB: `{ name, displayName, message? }`), archivedAt (soft delete), stepNameToTest (nullable), stepsCount.

- **PRODUCTION runs and the runs-metadata queue.** A PRODUCTION run's row is never written directly by the request that creates or updates it — `queueOrCreateInstantly`/`uploadRunLog` hand a `RunsMetadataUpsertData` object to `runsMetadataQueue(log).add()`, and only that queue's drain worker (`flow-runs-queue.ts`) actually calls `flowRunRepo().save()`/`.update()`. `runsMetadataQueueFactory`'s `stripToRunsMetadataUpsertData` strips every field not on its own `RUNS_METADATA_UPSERT_KEYS` whitelist before the value is even merged into Redis — **a new `FlowRun` column that a creation-time caller needs persisted for a PRODUCTION run must be added to that whitelist too, or it silently never reaches Postgres for PRODUCTION runs while working fine for TESTING runs** (which `save()` synchronously, bypassing the queue entirely). This exact gap shipped once: `parentWaitpointId` was added to the entity and to `queueOrCreateInstantly`'s in-memory `FlowRun` object, but not to the whitelist, so every PRODUCTION subflow child silently lost its waitpoint proof before the drain ever wrote the row (#521). Separately, `buildFlowRunUpdate` (the *update*, not creation, path `uploadRunLog` drives) deliberately excludes `parentWaitpointId` on purpose — the engine must never be able to set or change it after creation; only the creation-time `save()` (server-verified via `resolveVerifiedParent`) may write it.
- **Legacy rows and the `parentWaitpointId` backfill.** A child created before the `parentWaitpointId` column existed can carry `failParentOnFailure: true` with no stored proof — `markParentRunAsFailed` (`flow-runs-queue.ts`) refuses to guess and completes nothing for such a row, logging a warning; the parent stays `PAUSED` until manually retried or cancelled. The `BackfillParentWaitpointIdFlowRun` migration (run after `AddParentWaitpointIdToFlowRun` adds the column, so the ALTER's lock is released first) backfills this once, for non-terminal (`QUEUED`/`RUNNING`/`PAUSED`), non-`INLINE` rows already in Postgres at migration time, matched against the parent's own `PENDING WEBHOOK` waitpoint **only when the parent has exactly one** (same `projectId` as the child) **and it was created no later than the child** — zero or multiple candidates, or a later waitpoint, are left `NULL`, since there is nothing safe to guess. This is a one-time backfill, not a fail-time fallback: a webhook job queued by the pre-deploy API but not landed in Postgres until after the migration ran, or a split-version deploy where an old-code instance is still creating children without this column, both still land in the "complete nothing" branch afterwards. Recovery in every unresolved case is the same: retry or cancel the stranded parent (#521).

## Endpoints

- `GET /` — List runs (cursor pagination, filters: projectId, flowId, status, tags, createdAfter/Before, failedStepName, failedStepMessage). Paginates by a composite `(created DESC, id DESC)` cursor — `id` is the unique tiebreaker that keeps page boundaries stable when runs share a `created` timestamp (e.g. same-transaction inserts). `failedStepMessage` is a case-insensitive `ILIKE '%…%'` against `failedStep->>'message'`. The status and failedStepMessage filters are independent — combining a non-failure status with a failedStepMessage simply returns empty (no implicit narrowing).
- `GET /:id` — Get single run with populated data
- `POST /:id/retry` — Retry single run (strategy: FROM_FAILED_STEP or ON_LATEST_VERSION)
- `POST /retry` — Bulk retry with filters
- `POST /cancel` — Bulk cancel paused/queued runs. Descendants are found via `getAllChildRuns`, a
  recursive CTE scoped by `projectId` at the anchor and on every hop — without that scoping, a run
  whose `parentRunId` was forged into another project (see the webhook doc's `ap-parent-run-id`
  note) could let that project's cancel reach a foreign project's run (#521)
- `POST /archive` — Bulk soft delete (set archivedAt)
- `POST /v1/waitpoints` — Engine-only: create a waitpoint (PENDING) for a paused step
- `ALL /:id/waitpoints/:waitpointId` — Resume a paused run via waitpoint (V1, async)
- `ALL /:id/waitpoints/:waitpointId/sync` — Resume and return the flow's response synchronously (V1)
- `ALL /:id/requests/:requestId` — V0 legacy resume route (pauseMetadata-based)
- `ALL /:id/requests/:requestId/sync` — V0 legacy sync resume

## Retry Strategies

- **FROM_FAILED_STEP**: Default path fetches execution state from zstd-compressed logs file, rebuilds FlowExecutorContext, re-runs from failed step. Previous step outputs preserved. Enqueued with `executionType: RESUME` and `resumeReason: RETRY` so the engine drops the FAILED step from the restored journal — without this, the failed step would be treated as already-complete and the retry would be a no-op. **Special case — failed trigger:** when `oldFlowRun.steps[trigger.name].status === FAILED`, there is nothing to RESUME from (the trigger never produced a real output). The retry instead enqueues `executionType: BEGIN` + `executeTrigger: true` and feeds the raw event preserved on the trigger step's `output` field back as `triggerPayload` so `pieceTrigger.run()` re-executes against the (now-fixed) connection. Same `flowVersionId` as the original run.
- **ON_LATEST_VERSION**: Starts fresh from trigger on latest published version. Reads the payload from `triggerStep.output` for both cases — `executeTrigger` is the discriminator. Normally `executeTrigger: false` (the previous trigger's `run()` result is replayed as-is). When the previous run's trigger step is FAILED, switches to `executeTrigger: true` so `pieceTrigger.run()` reprocesses the raw event (stored in the same `output` field) and produces correctly-shaped output for downstream actions.
- **Failed-trigger payload preservation**: `flow.operation.ts#buildFailedTriggerContext` writes `input.triggerPayload ?? {}` into the failed trigger step's `output` field via `.setOutput(...)` — the same slot a successful trigger uses for its `run()` result, so retry reads `triggerStep.output` uniformly and the existing output-slicing machinery covers large payloads. This is the only place the raw event survives past the BullMQ job's completion — the job is removed on `removeOnComplete: true`, so without this both retry strategies would have no event to re-trigger from. The `executeTrigger` flag (set from `status === FAILED` at retry time) is what distinguishes replaying a processed result from reprocessing a raw payload; no separate payload field is needed. **This only holds when the trigger's output was actually logged** — see the next bullet.
- **Redacted-trigger refusal (#505 review fix)**: if the flow version the old run actually executed on had `trigger.logOutput === false`, or the old run's persisted trigger step output is the `**REDACTED**` placeholder, both strategies refuse the retry with a `QadamFlowError({ code: ErrorCode.VALIDATION, params: { message } })` instead of replaying `**REDACTED**` as the trigger payload — `flow-run-service.ts#assertTriggerPayloadRetryable`, checked against the version the run ran on (never the latest/target version, which may have logging back on). The check runs before any run-row mutation, so a refused retry leaves the old run untouched. `bulkRetry` already isolates per-run failures via `Promise.allSettled`, so one redacted run in a batch does not abort the others; `ap_retry_run` surfaces the message through `mcpUtils.mcpToolError`'s existing `VALIDATION` handling. The message tells the caller why (trigger logging was off, so the payload was never kept) and what to do (re-trigger with a fresh event, or turn trigger logging back on for future runs).
- Constraint: only terminal states, within retention window (EXECUTION_DATA_RETENTION_DAYS).

## Logs Storage

- Stored as File entities with type FLOW_RUN_LOG
- Compressed with zstd before upload
- Worker uploads via JWT-signed URLs (7-day expiry)
- State backed up every 15s during execution for crash recovery
- **Per-step redaction (#389 / #451 / #505):** an action's `logInput` / `logOutput: false` and a
  trigger's `logOutput: false` replace that step's persisted input/output with `**REDACTED**`
  (`packages/server/engine/src/lib/helper/log-redaction.ts`); the live value still flows to the
  next step. The trigger has no `logInput`: its logged input is configuration, the payload that
  carries user data is its output. Outputs stay raw while a run is PAUSED (RESUME hydrates from
  the log) — so the trigger payload is visible until the run finishes — and are redacted by the
  terminal backup once it does. Settable from the builder (`StepLogSettingsForm`) and from MCP
  (`ap_add_step` / `ap_update_step` / `ap_build_flow` / `ap_update_trigger`), visible in
  `ap_flow_structure`. **A run whose trigger `logOutput` was off cannot be retried** (#505 review
  fix) — see the Retry Strategies section.

## Pause & Resume

- **Waitpoints (V1, current):** pieces call `ctx.run.createWaitpoint({ type, ... })` + `ctx.run.waitForWaitpoint(id)`. Engine POSTs `/v1/waitpoints`; server inserts a PENDING row keyed on `(flow_run_id, step_name)`.
  - `DELAY` waitpoint: server upserts a `SystemJobName.RESUME_DELAY_WAITPOINT` BullMQ job scheduled at `resumeDateTime`. When it fires, `resumeService.resumeFromWaitpoint` enqueues the resume.
  - `WEBHOOK` waitpoint: resume signal arrives as an HTTP call on `/:id/waitpoints/:waitpointId[/sync]`. Optional `responseToSend` is replied immediately to the original webhook trigger. Its id doubles as a second job: `waitpointService.existsPendingWebhookWaitpoint` lets webhook ingress prove `ap-fail-parent-on-failure` actually came from this waitpoint's own run, and the exact id is persisted on the child as `flow_run.parentWaitpointId` so `markParentRunAsFailed` completes only that row — see `webhooks.md`'s `callbackUrl`-derived proof note (#521 impact item 3).
  - `DELAY` job id is per waitpoint (`waitpointJobIds.resumeDelay`, `resume-delay-<runId>-<waitpointId>`): `upsertJob` skips a job id still taken, and a durable loop (#387) creates its next checkpoint waitpoint while the job that resumed the previous one can still be active. The job goes through `resumeService.resumeDelayWaitpoint` → `handleResumeSignal` whatever the run's state — a run still RUNNING/QUEUED (a budget checkpoint is due at once) gets its waitpoint COMPLETED and the PAUSED upload resumes it; skipping it would strand the run PAUSED.
  - **Join waitpoint (#374):** a `WEBHOOK` waitpoint created with `join: { slots, failurePolicy, quorum?, timeoutSeconds? }` (`@aiqadam/qadam-subflows` `callFlowForEach`, `pauses: true`). `createForPause` inserts it and its `waitpoint_slot` rows (`id` = the slot's secret, `slotIndex`, `status` PENDING/SUCCEEDED/FAILED/TIMED_OUT, `payload` text = serialized answer capped at `JOIN_SLOT_MAX_DATA_BYTES` 64 KB, `childRunId`; UNIQUE(waitpointId, slotIndex); CASCADE on waitpoint and project) in one transaction, and hands back `slotResumeUrls` — `/v1/flow-runs/:id/waitpoints/:waitpointId/slots/:slotId`, one per child. `joinWaitpointService.fillSlot` locks the waitpoint FOR UPDATE, writes the slot first-answer-wins, and when `joinPolicy.decide` says so (ALL_SETTLED: every slot answered; FAIL_FAST: first failure; QUORUM: `quorum` succeeded, or out of reach) marks the waitpoint COMPLETED with `{ status: success|error, data: { results[i]: { status: success|error|timeout|pending, data }, succeeded, failed, timedOut } }` and resumes through `resumeFromWaitpoint` — the same PAUSED / pre-completion handling as any waitpoint, so fast children that answer before the parent reports PAUSED are counted, not lost. A PENDING join is never completed by the plain routes (`refusesJoinWaitpoint` in `resume-controller.ts`), by `complete()` (`join IS NULL`), nor by `markParentRunAsFailed`; a COMPLETED one resumes only with its stored aggregate. A child that ends without answering (failed, stopped, timed out, or SUCCEEDED with no Return Response) gets its slot answered by the runs-metadata drain (`fillSlotForFinishedChild`). `timeoutSeconds` (capped by `AP_PAUSED_FLOW_TIMEOUT_DAYS`) schedules `SystemJobName.JOIN_WAITPOINT_TIMEOUT` (`joinWaitpointService.expire`): unanswered slots become timed out and the run resumes with what arrived. At most `JOIN_WAITPOINT_MAX_SLOTS` (500) slots, and one PENDING join per run. Each answer decides from a per-status `COUNT`; the answers themselves are read once, when the join completes. A slot belongs to the first child created for it (`waitpointService.claimSlot`, from `queueOrCreateInstantly`): a replayed parent step gets its join back with `dispatchedSlots` (slots with a child or an answer — all of them once completed) and dispatches only the rest, and a second child for a claimed slot is not attached to the join (its own Return Response can still answer the callback URL it carries; first answer wins). A claim is released if the child run cannot be created or queued, and only the claimant answers its slot by finishing. An early decision (FAIL_FAST, QUORUM) does not stop the children still running; their answers are dropped.
- **Pre-completion (resume-before-pause race):** `waitpoint-service.complete()` takes a pessimistic write lock on the PENDING row. If a PENDING row already exists, it flips it to COMPLETED with the `resumePayload`, `workerHandlerId` and `httpRequestId` (falling back to whatever was already on the row); if no PENDING row exists yet, there is nothing to attach the signal to and it is dropped (`{ completedExisting: false, waitpoint: null }`) rather than inserted. When the flow then transitions to PAUSED, `flow-runs-queue.ts`'s drain calls `resumeFromWaitpoint` → `handleResumeSignal`, which sees the COMPLETED waitpoint and enqueues the resume immediately, using the `httpRequestId` persisted above so a caller still waiting on a sync response is the one who receives it. Prevents dropped early callbacks for the case a PENDING row already exists; a signal that arrives with no PENDING row at all is stale and correctly dropped.
- **On resume:** fetch state from logs file → rebuild `FlowExecutorContext` → re-run the paused step with `ExecutionType.RESUME` and `ctx.resumePayload = waitpoint.resumePayload`. When rebuilding `flowContext` in `flow.operation.ts#getFlowExecutionState`, steps in `SUCCEEDED` / `PAUSED` are always restored; `FAILED` steps are restored iff `resumeReason === WAITPOINT`. Dropping a FAILED step kept alive by `continueOnFailure` would re-execute it from BEGIN — re-firing its waitpoint (e.g. re-invoking a subflow) and letting the global `constants.resumePayload` pollute the new output. The retry path needs the opposite behavior, hence the discriminator.
- **Limits:** `AP_PAUSED_FLOW_TIMEOUT_DAYS` caps DELAY `resumeDateTime`; engine throws `PausedFlowTimeoutError` beyond that.
- **Legacy (V0) path:** `pauseMetadata` on `flow_run` + `ctx.run.pause({ pauseMetadata })` + `ctx.generateResumeUrl()` + `/requests/:requestId[/sync]` routes. `resume-controller.ts` resolves the run (`findFlowRunForLegacyResume`) and, if a PENDING V0 waitpoint exists for it, resumes through the same path the V1 waitpoint routes use — which re-resolves the run a second time inside `resumeFromWaitpoint`, safely, since `handleResumeSignal`'s pessimistic lock on the waitpoint row makes that second read race-proof. Otherwise it falls to the no-waitpoint legacy branch (`resumeService#legacyResume`/`legacySyncResume`), which takes the already-resolved row and never re-fetches it (closing a check-then-use gap that used to exist there), and requires ALL of: `status === PAUSED`; `pauseMetadata` parses as a pre-shim WEBHOOK pause (`isEligibleForLegacyNoWaitpointResume`, zod-narrowed via `WebhookPauseMetadata`, never a cast); and the run has NO waitpoint row at all, of any status or version (`waitpointService#hasAnyWaitpoint`). That third condition exists because every resume URL — V0 or V1 — embeds the run id, so holding an *earlier* approval link for a run would otherwise be enough to resume that run's *current*, unrelated PENDING waitpoint through this run-id-only route. Anything that fails the combined guard gets the same "stale" response as an expired/already-used link (200 with an expired-link body for the async route, 410 for `/sync`) — not a 404 and not a status-specific 409. Since the piece-API pause shim (`buildLegacyPauseHook`, deployed 2026-04-13) every `run.pause()` call creates a real waitpoint row itself (and `process.exit(1)`s if that write fails), so only a run paused by a pre-shim engine can still reach the no-waitpoint branch — bounded by this platform's configured execution-data retention (`FILE_CLEANUP_TRIGGER` purges `FLOW_RUN_LOG` files past `AP_EXECUTION_DATA_RETENTION_DAYS`, and `PAUSED_FLOW_TIMEOUT_DAYS` is capped at that same retention). Safe removal date = shim deploy date (2026-04-13) + this deployment's configured retention (30 days by default; later if retention was raised).
- **On server restart:** `refill-paused-jobs` migration re-queues legacy paused runs. Waitpoint DELAYs are BullMQ delayed jobs and survive restarts natively.

## Frontend Integration

`flowRunsApi.subscribeToTestFlowOrManualRun()` uses Socket.IO to start a test run and stream progress updates via `WebsocketClientEvent.UPDATE_RUN_PROGRESS`. The builder's run-list sidebar polls for recent runs (infinite query, auto-refetching every 15s while runs are still executing) and deduplicates entries by `id` when flattening pages — a safeguard against page overlap during live refetch. The run-details panel renders step-by-step input/output from the populated run's execution logs. `flowRunMutations.useRetryRun` handles the `FLOW_RUN_RETRY_OUTSIDE_RETENTION` error code with a user-facing toast showing the retention window.

### Runs Table Filters

The runs table surfaces a Status multi-select and an "Error message" text input (`failedStepMessage` URL param). Filters are independent AND'd dimensions — the backend applies them with no implicit narrowing. Combining a non-failure status with `failedStepMessage` returns empty (only `FAILED_STATES` runs carry `failedStep.message`); the conflict is left for the user to resolve via the visible chips.

### Failed-Step Surfaces

- **Runs table failed-step column** renders the failed step's display name with a tooltip showing the truncated, JSON-pretty error message; clicking opens `FailedStepDialog` (full error + "Go to run" footer). Legacy runs without a captured message bypass the dialog and navigate straight to the run page.
- **Builder run-info widget** shows up to two controls during a run:
  - A "Follow run updates" button — visible only while the run is non-terminal and the user has manually selected a different step. Clicking it calls `resumeLiveFollow`, which clears the `userManuallySelectedStepDuringRun` flag and snaps loop indexes to their latest iteration so the canvas resumes following the engine live.
  - On failure, a "See error" button that focuses the failed step on the canvas via `goToFailedStep` in `run-state`.
  - Live-follow itself is gated by `userManuallySelectedStepDuringRun` in `canvas-state`: `selectStepByName` sets it whenever the user picks a different step mid-run (`fromAutoFocus` is passed when the change came from the auto-follow effect, not a user click), and `setRun` resets it when a new run id arrives.
