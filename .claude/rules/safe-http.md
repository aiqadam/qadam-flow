For any outbound HTTP in `packages/server/{api,worker,utils}`, use `safeHttp.axios` or `safeHttp.createAxios({ ... })` from `@aiqadam/server-utils`. These wrap `request-filtering-agent` to reject private, loopback, link-local, and cloud-metadata IPs (configurable via `AP_SSRF_ALLOW_LIST`).
Never call raw `fetch(...)` or `axios.create(...)` for URLs sourced from user input, admin config, OAuth token/refresh endpoints, or third-party integrations — they bypass SSRF protection and close the DNS-lookup-to-connect TOCTOU window the filtering agent handles.
For a library that accepts only a `fetch` override and no agent (the AI SDK provider factories are the case this exists for), pass `safeHttp.fetch` — a `fetch`-shaped front end over the same filtered axios instance, so the process keeps exactly one SSRF implementation. Do not reach for undici's `dispatcher` to build a second one. Pass it as a value (`fetch: safeHttp.fetch`), which is what every caller does and which the lint rule never flagged; *calling* `safeHttp.fetch(...)` is still an error everywhere except its own test, exempted by a one-file override in `packages/server/utils/.eslintrc.json` rather than by weakening the shared rule across `api`, `worker` and `utils`. Note `safeHttp.fetch` deliberately drops everything axios attached to a thrown error — an `AxiosError` carries the request config, and the config carries the provider API key, which `loggerRedact`'s static path list cannot cover for `x-api-key`, `api-key`, `x-goog-api-key`, `cf-aig-authorization` or a CUSTOM provider's operator-named header.
For a client that takes neither an axios instance nor a `fetch` override but does take Node `http.Agent`s — the AWS SDK's `requestHandler` is the case this exists for — pass `safeHttp.buildDefaultAgents()` into `new NodeHttpHandler({ ... })`. That is the same `request-filtering-agent` the axios instances wear, reading the same `AP_SSRF_ALLOW_LIST`; use it rather than `safeHttp.buildAgents({ allowList })`, which would make the caller re-parse the allow list and is how the live filter and the configured one drift apart.
**Importing an already-constructed client from another package is a bypass, not an exemption.** `httpClient` from `@aiqadam/qadams-common` is `new AxiosHttpClient()` — no filtering agent, and it sets `NODE_TLS_REJECT_UNAUTHORIZED=0` process-wide. Seven of the nine AI provider strategies imported it and so made unfiltered outbound requests from inside `packages/server/api` while matching none of the raw-`fetch`/`axios` lint patterns (#276). `no-restricted-imports` now names it, and three `no-restricted-syntax` selectors catch the names `httpClient` / `AxiosHttpClient` / `BaseHttpClient` arriving by any other route: `ImportSpecifier` for a deep import or a local re-export, `MemberExpression` for a namespace import or `require(...).httpClient`, and `ObjectPattern > Property` for `const { httpClient } = require(...)` / `= await import(...)`, which binds the name through neither of the other two. All six forms were checked against a probe file; the `ObjectPattern` one exists because the first two let it through.
Hardcoded calls to trusted Qadam Flow endpoints (e.g. `api.aiqadam.org`) must also go through `safeHttp.axios` / `safeHttp.createAxios({ ... })` — there is no separate `apAxios` helper.
This rule is lint-enforced (`no-restricted-syntax` / `no-restricted-imports` in `packages/server/.eslintrc.json`, inherited by `api`, `worker`, and `utils`) — a raw `fetch(...)`, `globalThis.fetch(...)`, `window.fetch(...)`-style member call, `axios.create(...)`, bare `axios(...)` call, or default `import axios from 'axios'` fails lint. `packages/server/utils/src/safe-http.ts` (the wrapper) is exempted via an override in its own `packages/server/utils/.eslintrc.json`. `packages/server/engine` is out of scope for this rule (it has its own SSRF defence — a global undici dispatcher plus a socket guard in `src/lib/network/ssrf-guard.ts`) and is exempted via an override in its own `packages/server/engine/.eslintrc.json`; both per-package overrides exist because `matchBasePath` in `@eslint/eslintrc` is inherited from the topmost config in an `extends` chain, so a shared-config override glob referencing a nested package path (e.g. `**/utils/src/safe-http.ts`) does not reliably resolve once that package has its own local `.eslintrc.json` — see the override's own directory-relative pattern for why.
